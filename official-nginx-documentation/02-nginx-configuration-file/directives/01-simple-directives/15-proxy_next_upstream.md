# proxy_next_upstream time ;
---
## ۱-چیست این دایرکتیو :

دستور `proxy_next_upstream` در Nginx مشخص می‌کند که در صورت بروز خطا یا شرایط خاص هنگام ارتباط با یک Backend، آیا Nginx درخواست را به Backend دیگری ارسال کند یا خیر.

به زبان ساده، این Directive برای مدیریت خطا و توزیع مجدد درخواست بین سرورهای Backend استفاده می‌شود.

---

## ۲-چرا این دایرکتیو ساخته شده و به قابلیتی که این دایرکتیو ایجاد کرده چه میگوییم

### چرا این Directive ساخته شده؟

فرض کن دو Backend داری:

- Backend 1
    
- Backend 2
    

ا-Nginx درخواست کاربر را به Backend 1 ارسال می‌کند، اما Backend 1 در دسترس نیست یا هنگام پردازش درخواست خطای مشخصی رخ می‌دهد.

در این شرایط Nginx می‌تواند درخواست را به Backend 2 بفرستد.

به این قابلیت می‌گوییم Failover.

---

### 3-ساختار دستور

```
proxy_next_upstream error timeout;
```

یعنی اگر هنگام ارتباط با Backend خطای ارتباطی یا Timeout رخ دهد، Nginx می‌تواند درخواست را به سرور بعدی در گروه Upstream ارسال کند.

---
### مثال واقعی

```
http {
    upstream backend_servers {
        server 127.0.0.1:8082;
        server 127.0.0.1:8083;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend_servers;

            proxy_next_upstream error timeout;
        }
    }
}
```

در این مثال:

1. درخواست به یکی از Backendها ارسال می‌شود.
    
2. اگر شرایط تعیین‌شده در `proxy_next_upstream` رخ دهد، Nginx تلاش می‌کند درخواست را به Backend دیگری ارسال کند.
    
3. اگر Backend بعدی بتواند پاسخ دهد، کاربر پاسخ را دریافت می‌کند.
    

### ۴. مقادیر قابل استفاده

|مقدار|مفهوم|
|---|---|
|`error`|خطای هنگام برقراری اتصال یا ارسال درخواست|
|`timeout`|وقوع Timeout|
|`invalid_header`|دریافت هدر پاسخ نامعتبر|
|`http_500`|دریافت پاسخ HTTP 500|
|`http_502`|دریافت پاسخ HTTP 502|
|`http_503`|دریافت پاسخ HTTP 503|
|`http_504`|دریافت پاسخ HTTP 504|
|`http_403`|دریافت پاسخ HTTP 403|
|`http_404`|دریافت پاسخ HTTP 404|
|`off`|غیرفعال کردن تلاش مجدد|

### ۵. اهمیت در Production

اهمیت زیاد

این Directive در معماری‌هایی که چند Backend دارند اهمیت زیادی دارد، زیرا:

- به افزایش دسترس‌پذیری سرویس کمک می‌کند.
    
- در زمان خرابی یک Backend امکان استفاده از Backend دیگر را فراهم می‌کند.
    
- احتمال شکست درخواست را در شرایط قابل‌بازیابی کاهش می‌دهد.
    

یک نکته بسیار مهم در Production:

Nginx همیشه نمی‌تواند درخواست را مجدداً ارسال کند. برای مثال، اگر درخواست غیرقابل‌تکرار باشد یا بخشی از پاسخ قبلاً به کاربر ارسال شده باشد، محدودیت‌هایی وجود دارد.

همچنین برای درخواست‌های غیر `GET` باید به احتمال اجرای دوباره عملیات توجه کرد؛ مثلاً ممکن است یک درخواست پرداخت در Backend اول اجرا شده باشد ولی پاسخ آن به Nginx نرسیده باشد. تکرار درخواست می‌تواند پرداخت را دوباره انجام دهد.

پس `proxy_next_upstream` ابزار مهمی برای Failover است، اما باید با توجه به نوع درخواست و معماری Backend تنظیم شود.
